# Risk register

These risks can invalidate the product even if the implementation works. Review
the register at every phase boundary and record evidence when severity changes.

| Risk | Early warning | MVP control | Stop/expand trigger |
|---|---|---|---|
| Stale or wrong guidance | reports contradict a verified route; blinded sessions fail | visible freshness state, 30-day review, immediate stale flag, immutable corrections | stop catalog growth if five-route maintenance model fails |
| No developer demand | praise but no keys used or integrations completed | sandbox task with three qualified partners | stop backend expansion if Phase 5 integration gate fails |
| Game attracts no attention | low completion, replay, or sharing | three-level behavioral test with pre-registered thresholds | replace the growth wedge; do not reinterpret API demand |
| Collection cost overwhelms value | verification time/change rate grows faster than coverage | manually measure five routes for four weeks | do not automate until process failure is understood |
| Legal, terms, or trademark dispute | takedown request or counsel flags interface reproduction | private pilot, semantic text only, source/evidence log, withdrawal process | obtain qualified legal review before public brand-scale launch |
| Personal information enters reports | PII scanner or moderator finds account data | structured fields, short notes, rejection probes, no screenshots | block submissions after any public/log leak until remediated |
| Malicious or coordinated reports | duplicate spikes or attempts to mark a route incorrectly | API identity, rate limits, deduplication, moderation, no direct publish | add stronger reputation/abuse controls before wider access |
| Cancellation causes unintended harm | user loses benefits/data or misunderstands outcome | informational language, prerequisites, confirmation state, no automation | withdraw affected route immediately and investigate |
| Service blocks verification | login gates, region ambiguity, account eligibility differences | explicit variant and unavailable/provisional states | exclude the service rather than invent a universal route |
| Competitor closes the data gap | adjacent directory ships equivalent verified graph API | interview partners on differentiated fields and freshness | narrow vertical or stop if no defensible user value remains |
| Webhook abuse or data exfiltration | callbacks target private networks or repeatedly fail | HTTPS allow rules, SSRF controls, signed events, bounded retries | no webhook launch until adversarial network tests pass |
| API key compromise | anomalous usage or leaked test key | hashed keys, rotation/revoke, quotas, secret scanning | revoke immediately; complete incident review before restoring |

## Required reviews before public launch

- Qualified legal review of data sourcing, interface text, trademarks, terms of
  service, takedown handling, and jurisdictional claims
- Threat model for observation input, admin publication, API keys, webhook SSRF,
  logs, backups, and dependency supply chain
- Privacy review demonstrating the service does not require consumer identity
- Accessibility review of the reference challenge
- Restore drill and credential-rotation drill

These reviews are release gates, not assertions that the project is legally or
technically safe today.
